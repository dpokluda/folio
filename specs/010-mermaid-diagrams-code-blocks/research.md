# Research: Mermaid Diagrams & Code Block Enhancements

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-08-12 (reconstructed 2026-10-18)

These decisions were reconstructed from the code comments and diffs of `1ce68e0` (2026-08-12) and `5c3ee89` (2026-08-20). Quoted rationale comes from the source comments. The Technical Context had no open unknowns, so every entry below records a decision already made in the shipped code.

### R1. Diagram engine and where diagrams enter the render pipeline

- **Decision**: Bundle Mermaid (`mermaid` `^11.16.1`) and draw diagrams asynchronously into empty placeholders, but only after the DOMPurify-sanitized HTML has been injected into `#write`. Mermaid's SVG output never passes through DOMPurify. It is initialized with `startOnLoad: false` and `securityLevel: 'strict'`, and Folio calls it explicitly from `renderMermaidBlocks()` in `src/renderer/renderer.js`.
- **Rationale**: "mermaid's own output never passes through DOMPurify (it would lose the embedded `<style>` and the `<foreignObject>` wrappers used for HTML labels). That is safe because mermaid sanitizes the diagram source itself under securityLevel:'strict', which also disables raw HTML and click handlers." Mermaid is the syntax Typora and GitHub use for ```` ```mermaid ```` fences, so the same documents work in all three. Bundling keeps Folio offline-capable (Principle VI), and with `startOnLoad: false` Folio alone decides when diagrams are drawn.
- **Alternatives considered**: Running the SVG through DOMPurify would strip the `<style>` and `<foreignObject>` it needs, and allowing those elements would widen the sanitizer allow-list for the whole document. Mermaid's `loose` or `antiscript` levels would let untrusted documents enable HTML labels or click callbacks. Its `sandbox` level (one iframe per diagram) would complicate sizing, fonts, find and printing. Loading Mermaid from a CDN is prohibited by Principle VI.

### R2. Handing diagram source from the Markdown renderer to the drawing pass

- **Decision**: Override markdown-it's `fence` rule. When the first word of the unescaped, trimmed info string is `mermaid` (case-insensitive) and the render `env` has a `mermaid` array, push `token.content` onto `env.mermaid` and emit `<div class="folio-mermaid" data-folio-mermaid="<index>"></div>`. Every other fence falls through to the default rule and therefore to the `highlight` hook. `renderPreview()` creates a fresh `env = { mermaid: [] }` for each render.
- **Rationale**: "Passing an index rather than the code itself keeps the markup small and avoids a round trip through HTML escaping." DOMPurify keeps `data-*` attributes by default, so the index survives sanitization, and a per-render `env` keeps indexes from leaking between documents.
- **Alternatives considered**: Storing the source in a `data-` attribute or a hidden `<pre>` would mean an escaping round trip and larger markup, and the hidden text would still be visible to find. Post-processing `<code class="language-mermaid">` blocks after rendering would have to undo the highlighter's markup.

### R3. Drawing order, unique ids and stale results

- **Decision**: Draw the placeholders one at a time (`for … of` with `await mermaid.render(id, code)`), giving each diagram the id `folio-mermaid-<generation>-<n>`. The module-level `mermaidGeneration` counter is bumped on every pass. After every `await`, the pass checks `gen !== mermaidGeneration || !el.isConnected` and abandons itself if either is true. A `finally` block removes Mermaid's scratch element `d<id>`. The whole pass is a promise kept in `mermaidPending`, with a trailing `.catch` that logs instead of leaving an unhandled rejection.
- **Rationale**: "an in-flight diagram whose generation is stale simply stops, so results from a previous document can never land in the new one after a fast file switch." "mermaid measures in a scratch element appended to `<body>`; it is not always cleaned up when a diagram fails to parse." Unique ids keep the id-scoped styles and markers that Mermaid embeds in each SVG from colliding across diagrams and passes. `initialize()` runs once at the start of each pass, so every diagram in a pass shares one configuration. Drawing one diagram at a time keeps results in document order and gives the pass a point between diagrams at which to stop.
- **Alternatives considered**: Drawing in parallel with `Promise.all` would gain nothing, because drawing is CPU-bound on the renderer's single thread, and it would complicate error isolation and abandoning a pass. `mermaid.run()` over DOM nodes gives less control over ids, errors and staleness. Abort-style cancellation is not available because `render()` cannot be aborted; the generation check gives the same effect.

### R4. Diagram palette and font

- **Decision**: On every pass, `initMermaid()` calls `mermaid.initialize()` with `theme: 'dark'` when `matchMedia('(prefers-color-scheme: dark)').matches`, otherwise `'default'`. It also passes `fontFamily`, taken from `getComputedStyle($write).fontFamily` and omitted if empty. It sets `suppressErrorRendering: true` as well (see R5).
- **Rationale**: Appearance is applied by flipping `prefers-color-scheme` through `nativeTheme` (Principle I), so the same media query is the single source of truth. "Mermaid measures label text against its configured font, so feed it the active theme's body font instead of its own default. Recomputed on every pass (initialize() is cheap) so a theme or appearance switch is picked up without any extra bookkeeping." Mermaid bakes both palette and font into the SVG, which is why redraws are needed (R6).
- **Alternatives considered**: Mermaid's `base` theme with `themeVariables` derived from each Style's palette would be more faithful to each Style, but every theme's colours would have to be mapped; diagrams use Mermaid's built-in light and dark palettes instead (F5). The `neutral` and `forest` themes do not track dark mode. Overriding SVG colours with CSS is fragile because Mermaid embeds id-scoped styles.

### R5. A diagram that fails to draw

- **Decision**: Pass `suppressErrorRendering: true` so Mermaid draws no error graphic of its own. When `render()` throws, `renderMermaidError()` adds `folio-mermaid-error` and replaces the placeholder with `<pre class="md-fences"><code class="cm-s-inner">` (escaped source), followed by `<p class="folio-mermaid-message">` holding `err.message || err.str || 'Invalid diagram'` (escaped). It then attaches a copy button, because the fallback is created after the document-wide sweep. The message is styled monospace with `white-space: pre-wrap`, in red (`#b31d28` light, `#f85149` dark).
- **Rationale**: "A diagram that does not parse falls back to the source as a plain code block plus the parser's complaint, so a typo costs one diagram rather than hiding the content entirely." "The parser points at the offending column with a caret on its own line, so the message only reads correctly in a monospace font with its newlines and leading runs of spaces preserved." Each diagram has its own `try`/`catch`, so one failure never stops the pass.
- **Alternatives considered**: Mermaid's built-in error SVG ("bomb" graphic) hides the source and does not match the theme. Leaving the failed fence as highlighted code without a message would not tell the user what is wrong. Aborting the whole pass on the first error would lose every diagram after it.

### R6. Redraw triggers: appearance flips and theme changes

- **Decision**: `src/main.js` listens to `nativeTheme.on('updated')` and sends `appearance-changed` to every session. `src/preload.js` exposes it as `folioAPI.onAppearanceChanged`, and the renderer responds with `setTimeout(refreshMermaid, 0)`. `applyTheme()` collects a promise for each new `<link class="folio-theme">` that resolves on `load` or `error`, then calls `refreshMermaid()` after `Promise.all`. `refreshMermaid()` does nothing in source mode or when the document has no `[data-folio-mermaid]` placeholder; otherwise it re-renders the preview.
- **Rationale**: "Chromium updates the media query's *value* in the renderer but does not dispatch a `change` event for it, so anything that has to react in script (mermaid diagrams bake their palette into the generated SVG) needs an explicit nudge." "Deferred with a timer (not requestAnimationFrame, which Chromium suspends for background windows) so the page has settled on the new appearance before mermaid reads it." "A new theme can change the body font that mermaid measured against, but only once its stylesheets are actually in effect." Appearance is app-wide ([004](../004-three-axis-theming/spec.md)), so every window is notified. Because the hook sits on `nativeTheme` itself, the live OS flips that [011](../011-system-appearance/spec.md) later enabled (`themeSource = 'system'`) redraw diagrams with no further work.
- **Alternatives considered**: A renderer-side `matchMedia(...).addEventListener('change')` does not fire for `nativeTheme` flips, as the comment explains. Deferring to the next animation frame would stall background windows; a stale duplicate comment in `boot()` ("Deferred a frame…", see F3) suggests an earlier version did exactly that. Redrawing only the diagram nodes instead of the whole preview would need more code, and the full re-render is cheap and skipped when a document has no diagrams.

### R7. PDF export waits for diagrams

- **Decision**: In the renderer, the `prepare-export` handler leaves source mode (which re-renders the preview and starts a new pass) and returns `whenMermaidSettled().then(() => true)`. `whenMermaidSettled()` is `mermaidPending.catch(() => {})`. In the main process, `doExportPDF()` calls `ask(session, 'prepare-export', { fallback: true, timeoutMs: 20000 })` instead of using `ask()`'s default 4000 ms.
- **Rationale**: "Diagrams draw asynchronously; printing before they settle would capture empty placeholders." "Diagrams are drawn asynchronously, so allow more time than a plain content request." With `fallback: true`, export still works when the renderer does not answer (the existing `ask()` design), and the cap keeps the wait bounded (Principle VI).
- **Alternatives considered**: A fixed delay before printing is too short for large documents and wasteful for small ones. Drawing diagrams synchronously is impossible because Mermaid's `render()` is async, and it would block the UI anyway. A separate export pipeline that rasterizes diagrams would duplicate the preview path.

### R8. Copy button design

- **Decision**: After sanitization, `addCopyButtons()` adds one `<button type="button" class="folio-copy" contenteditable="false">` to every `#write pre.md-fences` whose `<code>` has non-blank text. The button holds an inline SVG icon and no text. Its label is set through `title` and `aria-label` ("Copy code", "Copied", "Copy failed"). A click calls `preventDefault()` and `stopPropagation()`, then copies `code.textContent` minus one trailing `\n` with `navigator.clipboard.writeText()`. Confirmation is a check icon plus `folio-copy-done`, or the copy icon plus `folio-copy-failed`, and a per-button 1400 ms timer stored in a `WeakMap` resets it. In CSS, the fence becomes `position: relative` and the 26×26 px button sits 6 px from its top-right corner. The button has `opacity: 0` until `pre.md-fences:hover` or `:focus-visible`; the done and failed states are pinned visible, and the button has `user-select: none`. It has a dark palette and is hidden by `@media print`.
- **Rationale**: The button is icon-only because "#write is walked verbatim by the find-in-page highlighter and the outline builder, so a textual 'Copy' label would show up as a bogus search match and could be swept into a text selection." "The button lives inside the `<pre>`, whose content is whitespace-sensitive and user-selectable; keep it out of both." "Fences render with a trailing newline; pasting it would add a stray blank line at the end." "The themes don't position `.md-fences`, so making it the containing block here is safe; fences also don't scroll (long lines overflow visibly), so the button stays put without a wrapper element." "The button sits inside the `<pre>`, so it can never be hovered without the fence being hovered too — an invisible button is therefore never clickable." The renderer can write to the clipboard itself, so no privileged channel is needed (Principle III).
- **Alternatives considered**: A text "Copy" label would pollute find, the outline and selections. A wrapper element around each fence is unnecessary and would change the Typora DOM that themes target. A main-process clipboard channel (Copy File Path in [008](../008-source-editing-tools/spec.md) uses Electron's `clipboard`) would add an IPC surface for text the renderer already has.

### R9. Typora-identical highlighting engine

- **Decision**: Replace highlight.js with `src/renderer/highlight.js`, which drives the CodeMirror 5 modes published as `@codemirror/legacy-modes` directly, through `StringStream` from `@codemirror/language`. Like CodeMirror 5, it splits each style string on spaces and emits a `cm-` prefixed class for each part. The markdown-it `highlight` hook wraps the output in `<pre class="md-fences"><code class="cm-s-inner language-<first word>">`. The module also normalizes token names and resolves languages:
  - `TOKEN_ALIASES` folds the 63 Lezer-style names that modernised modes return (`variableName.local`, `angleBracket`, …) onto CM5 names, where `null` means emit no span. An unknown dotted name falls back to its base tag, and anything that is not a valid class name is dropped.
  - `resolveMode()` takes the first word of the info string, lower-cased, and looks it up as an own property of the 170-key `MODES` table (`php: null`). An unknown language, or a mode that throws, yields escaped plain text.
  - `runMode()` reports blank lines to the mode (`blankLine`), nudges a zero-width token forward, and stops tokenizing a line after `MAX_TOKENS_PER_LINE = 10000` tokens. It uses `TAB_SIZE = 4` and `INDENT_UNIT = 2`.
- **Rationale**: "Typora renders every fenced block with CodeMirror, so its themes colour code through `.cm-*` classes fed by the `--color-cm-*` palette. Folio used to highlight with highlight.js, whose `.hljs-*` tokens classify code quite differently — most visibly, highlight.js emits no token at all for bare identifiers, so type and variable names fell back to plain body colour where Typora paints them." The modes are "the *same* CodeMirror 5 modes Typora runs … driven directly here rather than through CodeMirror 6's Lezer bridge: the bridge maps CM5 token names onto Lezer tags, which is lossy in both directions, whereas reading the mode output straight gives the original CM5 names and therefore markup that is class-for-class identical to Typora's." On Lezer names: "Typora runs CM5, so its themes only style the CM5 vocabulary — and emitting a Lezer name verbatim would also produce a class containing a dot, which no sane selector matches." The modes reuse `@codemirror/language`, which is already bundled for the source editor, so only the mode package is new.
- **Alternatives considered**: Keeping highlight.js and mapping `.hljs-*` classes to theme variables would still classify tokens differently from Typora. CodeMirror 6's `StreamLanguage` with `highlightTree` maps tokens through lossy Lezer tags. Bundling CodeMirror 5 just for static highlighting would add a second editor library.

### R10. Palette coverage, fence size parity and bundle size

- **Decision**:
  - Delete the fixed GitHub light and dark highlight.js palettes from `app.css`.
  - Let the theme's `.cm-*` rules colour the tokens; `themes/base.css` maps them to `--color-cm-*` for every Style.
  - Add a fallback block scoped to `#write .md-fences` for the nine classes that Typora's core `codemirror.css`, not the theme, colours: `cm-string-2`, `cm-qualifier`, `cm-bracket`, `cm-quote`, `cm-positive`, `cm-negative`, `cm-error`, `cm-em` and `cm-strong`. The fallbacks use theme variables with literal defaults.
  - Add `#write .md-fences > code, #write .md-fences > tt { font-size: inherit }`.
  - Drop the obsolete `.md-fences .hljs` selector from the inner-code reset in `themes/base.css`.
  - Separately (`1ce68e0`), set `minify: !watch` in `build.js`.
- **Rationale**: "Typora splits that styling across two files … Folio loads only the theme, so the handful below would otherwise render as plain body text. Values come from the theme palette rather than Typora's hard-coded CM5 defaults (#f50, #997, ...) so they stay consistent in dark mode." The rules are "Scoped to the fence so they cannot leak into the CodeMirror 6 source editor." On font size: a theme rule such as `.md-fences, code, tt { font-size: 0.9em }` matches both the `<pre>` and its `<code>` in Folio's markup, so "the size compounds — 0.9em x 0.9em = 0.81em in Fluent/Word, and 85% x 85% = 0.72em in GitHub"; the `#write .md-fences > code` specificity "outranks every theme rule that sets this, so load order does not matter." On bundle size: "Mermaid is by far the largest dependency (it carries its own parsers and layout engines), which makes an unminified bundle slow to parse on every window open." Mermaid added 107 lockfile package entries. On 2026-10-18 the generated `src/renderer/bundle.js` in the working tree (last built 2026-09-30; an untracked artifact) measured about 4.9 MB. Source maps are still emitted and are excluded from packages by the existing `!**/*.map` rule.
- **Alternatives considered**: Copying Typora's core `codemirror.css` colours verbatim would give fixed light colours that are wrong in Dark. Editing every theme to stop the font-size compounding would break the "unmodified themes" promise. Lazy-loading Mermaid through code splitting would need ESM output with `splitting`, but the renderer is a single IIFE bundle (constitution). Leaving the bundle unminified would slow every window open.

## Retroactive findings

- **F1 — README drift (highlighting)**: Since `5c3ee89` (2026-08-20), README.md is stale in three places. The Features list still says fenced code blocks get "Syntax highlighting … with highlight.js". The Project layout describes `app.css` as holding "highlight.js token colors" and does not list `src/renderer/highlight.js`. The Acknowledgements credit highlight.js and do not credit `@codemirror/legacy-modes`. highlight.js is no longer a dependency. `5c3ee89` did not update README, which the constitution's Documentation gate requires. The spec describes the shipped CodeMirror 5 mode highlighter.
- **F2 — Stale highlight.js references in the repo**: The JavaScript sample in `samples/formatting-tour.md` still contains the comment "Fenced code is highlighted with highlight.js in the preview." The header comment of `build.js` still says "(markdown-it + CodeMirror 6 + highlight.js)". In `src/renderer/app.css`, the file header ("highlight.js token colours") and the code-fence font-size comment ("Folio (markdown-it + highlight.js)") are also stale.
- **F3 — Duplicated comment**: In `boot()` (`src/renderer/renderer.js`), an outdated paragraph ("Deferred a frame so the renderer has settled…") comes just before the corrected one ("Deferred with a timer (not requestAnimationFrame…)") above `onAppearanceChanged`. The duplicate was introduced in `1ce68e0` and is cosmetic only.
- **F4 — Diagram types**: README and the spec promise seven diagram types. Folio has no allow-list, so any type Mermaid 11.16.1 recognises is drawn as well (for example user journey, Git graph, mindmap and timeline). Only flowchart and sequence diagrams are exercised by the formatting tour.
- **F5 — Diagram palette scope**: Diagrams follow Light/Dark only, through Mermaid's built-in `default` and `dark` themes. A Style family's colours are not applied to diagrams; only its body font is. This matches README's wording ("Diagram colours follow the current Light/Dark appearance").
- **F6 — Limits of "Typora-identical"**: PHP is explicitly mapped to plain text because no legacy mode ships for it, and any name missing from the 169-name table (for example `markdown` or `text`) renders as plain text. The exported `hasLanguage()` helper in `src/renderer/highlight.js` is unused.
- **F7 — Links declared inside diagrams (code reading; not verified at runtime)**: Strict mode disables click *callbacks*, but according to Mermaid's upstream source it still emits `click … href` links as URL-sanitized `<a>` elements, and binds Gantt task links as `window.open(url, '_self')` handlers that Folio's `bindFunctions(el)` call attaches. Diagrams are drawn after `wireLinks()` has run, so these links bypass Folio's link routing and fall to the window guards in `src/main.js`: `http(s)` opens in the system browser, but `will-navigate` does not block `file://` targets. A follow-up review against Principle III is recommended, for example to wire or neutralise links inside drawn diagrams.
- **F8 — Find in document and diagrams (code reading)**: When the preview re-renders with the find bar open, matches are recomputed before the diagrams finish drawing, so diagram labels are not matched until the query is re-run. After that, the text walker also enters the drawn SVG, including the `<style>` text Mermaid embeds, which can yield matches that cannot be seen. The copy button deliberately avoids this problem (R8); diagrams do not.
- **F9 — Fallback palette specificity (code reading)**: The id-scoped `#write .md-fences .cm-…` fallback rules outrank a third-party theme's unqualified rules for the same nine classes unless those rules use `!important`. Those colours therefore come from the theme's `--color-cm-*` variables, with Folio's literal fallback values only where a variable is undefined, rather than from the theme's own rule for that class. The `font-size: inherit` rule outranks theme rules on purpose (R10).
- **F10 — Undocumented behaviour**: If diagrams are not drawn within 20 s, export proceeds without any notice and the PDF shows empty space where they belong. Drawn diagrams have no copy button; their source can only be copied in source mode. Indented (non-fenced) code blocks get neither a copy button nor colouring. Live redraw on OS appearance flips is described in README under **System**, which [011](../011-system-appearance/spec.md) owns.
- **F11 — Layout shift while diagrams draw (code reading)**: `loadDocument()` restores the reading position on reload, and scrolls to a heading anchor after link navigation, one animation frame after `renderPreview()`. That is usually before the asynchronous diagram pass has finished, so diagrams that appear above the target can push it down the page.
